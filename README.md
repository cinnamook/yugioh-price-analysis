# &lt;CYBERSE&gt;

A Yu-Gi-Oh! project that grew in three stages, all of which still live here:

1. **An analysis** — one cross-sectional question about what explains a card's price,
   answered from a single snapshot of the YGOPRODeck database.
2. **A data pipeline** — a daily collector that turns that one-off snapshot into a
   growing local price history in SQLite.
3. **An app** — <CYBERSE>, a personal collection / deck / budget / playtest hub, built
   as a single self-contained HTML page from that database, installable on a phone.

Live app: **https://cinnamook.github.io/yugioh-price-analysis/**

Nothing here is a framework or a server. The pipeline is stdlib Python, the app is a
static page generated by a Python script, and your data lives in your browser (with
optional Supabase sync).

`docs/` is the one confusing name, and it's forced: GitHub Pages can only serve from
the repo root or from a directory literally named `docs/`. Project documentation lives
in **`notes/`**.

Scripts resolve their paths from their own location, so you can run them from anywhere.
Generated pages (`app.html`, `screener.html`, `builder.html`, `deck_report.html`) are
always written to the repo root — on `file://` the app resolves card art relative to
itself, so it has to sit beside `data/`.

## 1. The analysis

**The question:** using a single snapshot of the YGOPRODeck database, which observable
attributes of a card — rarity, age, ban-list status, archetype, card type, reprint
history — are associated with its market price, and does ban-list status predict price
once scarcity is accounted for?

**The answer:** a card's price is driven mostly by **scarcity, not playability**. The
largest factors are rarity (each step up the rarity ladder adds roughly 30% to price)
and reprint history (a reprinted card is worth about a third less), with older cards
carrying a modest vintage premium. Ban-list status *is* associated with price —
Forbidden cards sell at roughly double an otherwise-comparable legal card — but this is
correlational and most likely reverse-caused: cards get banned *because* they are
powerful and iconic, which is the same thing that drives collector demand. The model
explains about **21%** of price variation; the remaining ~80% is competitive viability,
condition, and hype that a single snapshot of structural attributes cannot capture.

**Unit of analysis is the card** (~14k rows). Printings were the original choice, but the
data forced a reversal: `set_price` is $0.00 (no recorded sale) for **72%** of printings,
and that missingness correlates with trading volume and therefore with ban status —
which would have biased the one finding we care most about. So price is the card-level
**TCGplayer** price (96.5% coverage), and rarity enters as a card attribute.

The scope decisions, each justified against real numbers:

- **Unit of analysis** — cards *(reversed from printings, above)*.
- **Price source** — card-level TCGplayer price *(the cross-source spread is 12.9x)*.
- **Zeros / missing** — 510 cards (3.5%) at $0.00 = "no listing" → treated as missing and
  dropped (~13,967 analyzed); `log(0)` is undefined and a real 0 distorts averages.
- **Skew** — log-transform price *(mean $1.21 vs median $0.19; top 1% = 59% of value)*.
- **Reprints** — flag, don't exclude *(68% of cards are reprinted)*.
- **Ban-list format** — TCG; absence = Unlimited *(the 97.8% with no ban record are the
  control group, not missing data)*.

**What it is not:** a snapshot, not a time series — nothing about price movement or
ban-day crashes is answerable from it. Correlation only. Marketplace prices are asks,
not transactions. And cards still in print are not a random sample of cards ever printed.

Data: YGOPRODeck v7 REST API, free and public, pulled once in bulk with `misc=yes` and
cached at `data/cardinfo_misc.json`. The notebook reads the cached snapshot, so the
analysis is reproducible and never re-hits the API. Pull date **2026-08-05** — it's a
snapshot, so the date is part of the result. Card images are downloaded, never hotlinked
(per the API guide).

### Run it

```bash
pip install -r requirements.txt
jupyter notebook analysis/notebook.ipynb    # run top to bottom
```

The notebook applies every decision inline, with the reasoning in the markdown above
each step, and writes the analysis-ready table to `data/cards_clean.csv`.
`analysis/DECISIONS.md` is the worksheet behind those calls; regenerate its numbers with
`python3 analysis/profile_data.py`.

## 2. The pipeline

The analysis is a snapshot. The app needs history — and **price history cannot be
back-filled**, so the collector has to run every day from here on.

```bash
python3 pipeline/collect_snapshot.py     # append today's dated price row per card
```

Stdlib only, no venv needed. It appends one dated price row per card to
`data/ygo.db` and upserts card metadata, then applies the manual TCG ban-list
corrections in `pipeline/banlist_overrides.csv` on top of the source data.

**`data/ygo.db` is gitignored and irreplaceable once history accrues — back it up.**

To automate it on macOS (a 1pm launchd job that pulls *and* rebuilds the app):

```bash
bash scripts/setup_automation.command    # one time; writes the launchd job for you
```

That generates `~/Library/LaunchAgents/com.ryan.ygo-collector.plist` byte-for-byte
identical to the copy checked in at `pipeline/com.ryan.ygo-collector.plist`, so you can
`diff` the installed job against the repo. `notes/TOOL.md` has the cron equivalent.

## 3. The app

`app/build_app.py` reads `data/ygo.db` and writes **`app.html`**: one self-contained
page — vanilla JS, no framework, no build step, card data embedded as JSON. It holds
the collection, decks (main/extra/side), wishlist, bank/budget, playtest odds, a match
log, a sets browser, a meta watchlist, analytics, and a DuelingBook-style solo board.

All of the app's JavaScript lives *inside* `app/build_app.py` as a Python raw string.
**Edit the generator, never `app.html`** — that file is generated and gitignored. Your
data lives in the browser's localStorage and a rebuild never touches it.

```bash
python3 app/build_app.py      # rebuild app.html + the docs/ bundle
open app.html                 # desktop
```

```bash
bash scripts/refresh.command  # pull fresh prices, then rebuild (what the daily job runs)
bash scripts/publish.command  # rebuild, commit docs/, push -> updates the phone app
```

### Phone

The same page is emitted into `docs/` as an installable PWA (manifest + versioned
service worker) and served by GitHub Pages from `main` `/docs`. It works offline for
data, prices, decks and playtesting; only card art needs a connection. On desktop
(`file://`) the app uses the local `data/images/` cache; when hosted it uses the
YGOPRODeck CDN, which is what keeps the hosted bundle at ~15 MB instead of ~2.3 GB.
Fill that local cache with `python3 app/download_images.py --limit 500` in chunks.

Cross-device sync is optional and off unless the build has Supabase config
(`SUPABASE_URL` / `SUPABASE_ANON_KEY` in `app/build_app.py` — the publishable key is
public by design; the schema is `pipeline/sync_schema.sql`). Sign-in is an emailed
one-time **code**, not a clickable link, because on iOS a link authenticates Safari and
the installed PWA has separate storage. Details and setup traps: `notes/SYNC_DESIGN.md`.

`app/vendor/supabase.umd.js` is a third-party bundle **committed on purpose**: it is
pinned to one version with its sha256 recorded, `build_app.py` inlines it at build time,
and there is no package manifest that could restore it. Committing it is what lets a
fresh clone build a working, offline-capable app with no network and no install step.
`app/vendor/README.md` documents how to bump it.

### The earlier generators

`app/build_app.py` superseded these, but they still run and are useful on their own:

|---|---|
| `app/screener.py` | `screener.html` — filter/sort the whole catalog, plus a cross-marketplace "gap" flag |
| `app/deck_planner.py` | prices a `.ydk` decklist at a chosen rarity; cost-to-complete → `deck_report.html` |
| `app/build_builder.py` | `builder.html` — the standalone collection/deck/wishlist builder |
| `app/download_images.py` | fills the local card-art cache in `data/images/` |

```bash

```

## Gotchas

- Test the hosted/PWA path over **http** (`python3 -m http.server`), not `file://` —
  service workers don't run from `file://`, and the card-art base switches on protocol.
- When testing over http, **unregister the service worker first**. Its fetch handler
  answers navigations from cache and ignores the query string, so `?cachebust=` will
  silently serve you the *previous* build.
- The free YGOPRODeck API prices only ~30% of printings, and there is no free API for
  competitive meta — the meta list in the app is a manual watchlist by design.
